# RAG 系统 — 面试准备

## 简历描述

> **基于 Docling + ChromaDB 的混合检索 RAG 系统 | 个人项目**
> *2025.xx — 至今*
>
> 围绕文档解析与混合检索构建的完整 RAG 流水线。
>
> - 独立完成系统后端开发，涵盖用户登录、文档上传、文档管理、知识库问答等核心功能，并完成 FastAPI 与 Streamlit 的接口联调
> - 按文件类型选择不同加载器与分割策略，实现文档解析、文本切分与向量化入库流程，支持按用户维护独立向量库
> - 优化检索与上下文构建链路，在向量召回基础上结合 BM25、加权 RRF 与 MMR 压缩策略，提升复杂查询场景下的召回效果、结果相关性与上下文有效性
> - 在原有 RAG 架构基础上引入知识图谱构建链路，通过语义完整块切分进行实体识别与关系抽取，构建轻量级实体关系图结构，增强跨文档语义关联能力
> - 编写独立检索评测脚本，基于查询集与标注集计算 Recall@K、MRR@K 等指标，对召回效果与排序质量进行量化分析和迭代优化
>
> 技术栈：Docling, ChromaDB, BM25, RRF, MMR, GraphRAG, LangChain, FastAPI, Streamlit

## 面试追问与回答

### 一、系统架构与后端

#### 1. 整个系统架构是怎样的？前后端怎么交互？

FastAPI 作为后端提供 REST API，Streamlit 作为前端展示界面。Streamlit 通过 HTTP 调用 FastAPI 接口，包括文件上传、向量检索、问答等。FastAPI 侧采用异步 SQLAlchemy + MySQL 存用户和文档元数据，ChromaDB 存向量。用户上传的文档先落盘、记录入库，再异步走解析→分块→向量化流水线。

#### 2. 为什么用 FastAPI 做后端，Streamlit 做前端？Streamlit 本身就能做后端逻辑？

Streamlit 适合快速搭建 demo 界面，但它的执行模型是每次交互从头跑脚本，不适合复杂业务逻辑和长链路处理。FastAPI 做后端职责清晰——鉴权、文档管理、检索、问答各自独立路由，Streamlit 只负责调接口和渲染结果。两者拆开后也可以单独替换前端，比如后续换 Vue。

#### 3. 怎么保证多用户场景下数据不串用？独立向量库怎么实现的？

每条用户文档入库时记录 owner_id，ChromaDB 的 collection metadata 带用户 ID 过滤。实现方式是每个用户建一个独立 collection（如 `kb_user_1`），或在一个 collection 中通过 metadata 过滤。前者隔离更彻底，检索时直接指定对应 collection，不会跨用户检索。同时 FastAPI 依赖注入从 JWT token 中解析用户 ID，作为所有操作的租户标识。

#### 4. 文档上传做了哪些校验和处理？

文件类型白名单校验（PDF、Word、Excel、TXT、Markdown），大小限制，空文件检测。上传后先写磁盘、入 MySQL 记录元数据（文件名、大小、上传时间、处理状态），然后异步触发解析流水线。处理状态用枚举管理（pending → processing → completed / failed），前端轮询或回调展示进度。

#### 5. 知识库问答的完整链路是怎样的？

用户提问 → 向量化 query → ChromaDB 检索 Top-K 候选块 → 混合检索（+BM25）→ RRF 融合排序 → MMR 压缩去重 → 拼接 context → 与问题一起送入 LLM 生成答案。整个过程在 FastAPI 的 /qa 接口中同步完成，返回答案和引用来源。

### 二、文档加载与分块

#### 6. 为什么需要不同文件类型用不同加载器？

不同格式文档的内部结构差异很大。PDF 有页面布局、表格、图片，需要 Docling 做版面分析才能正确提取文本顺序和表格结构。Word 有标题层级和段落样式，Excel 是二维网格结构。纯文本和 Markdown 结构简单，LangChain 原生加载器性能好、无额外依赖。统一用一套加载器会导致表格数据错乱或图片内容丢失。

#### 7. Docling 解析 PDF 的实际效果如何？遇到过什么问题？

Docling 对纯文本型 PDF 效果很好，能保持段落结构和阅读顺序。但扫描件、图片型 PDF 需要额外 OCR，Docling 本身不做 OCR。另外复杂表格（合并单元格、跨页表格）偶有错乱。加了一些后处理逻辑：合并单元格重新对齐、跨页表拼接。

#### 8. 分块策略具体怎么做的？为什么不同文档用不同策略？

普通文本按 500 token 语义分块、50 token 重叠，保证块内语义完整且块间有衔接。表格不能横切——一行切断了数值就丢失上下文——所以表格按行批量处理，保持行级完整性，一个大表可能拆成若干行组。代码类文件按函数边界切。关键原则是：块边界尊重文档原始结构。

#### 9. 块大小 500 token 是怎么定的？有没有调过？

基于经验值——太小语义碎片化、太大检索精度下降。曾试过 300 和 800，300 导致一个概念被切成多块检索不到全景，800 导致噪声多、LLM 上下文利用率低。500 是实测折中，配合 50 token 重叠比较稳定。不同场景可以调，参数暴露在配置层。

#### 10. 为什么用 text-embedding-3-small 而不是其他模型？

性价比。1536 维向量，中文检索效果与 ada-002 相当但更便宜，且支持直接缩放到 512 维减少存储。如果后续需要更好的中文检索，可以考虑换 bge-m3 等中文专用模型。

### 三、混合检索与优化

#### 11. 为什么向量检索不够，还要加 BM25？

向量检索擅长语义匹配，但对精准关键词（如人名、地名、编号、专业术语）效果差——"第 38 号文件"这类查询向量检索可能召回一堆数字相近但语义无关的内容。BM25 天生擅长关键词精确匹配，两者互补。并行执行后合并结果，覆盖率和精确度都优于单一路径。

#### 12. RRF 是怎么融合向量和 BM25 结果的？

RRF（Reciprocal Rank Fusion）对两路检索结果按排名计算得分：`score = Σ 1/(k + rank_i)`，k 一般取 60。向量检索排第 1 和 BM25 排第 5 的文档，RRF 得分分别是 1/61 和 1/65，差距缩小，体现两路信号的综合置信度。加权 RRF 则对不同检索源赋不同权重，比如向量权重 0.7、BM25 权重 0.3，侧重语义匹配。

#### 13. MMR 压缩策略解决了什么问题？

检索回来的 Top-K 块可能有高度重复——同一个段落的两个相邻块语义高度相似，都给 LLM 就浪费 token。MMR 在选择时同时考虑相关性和多样性：既选择与 query 相关的块，又惩罚与已选块相似的块。最终上下文信息密度更高，同样 token 预算能覆盖更多不同方面的内容。

#### 14. MMR 的 λ 参数怎么调的？

λ 控制相关性与多样性的平衡：λ=1 只看相关性等同于普通排序，λ=0 只看多样性。实际取 0.6-0.7，保证主体与 query 相关的同时，避免连续选到同段落的不同切块。调参方式是跑评测脚本看不同 λ 下 Recall@K 和 MRR@K 的变化曲线。

#### 15. 整个检索链路的延迟大概多少？瓶颈在哪？

ChromaDB 向量检索通常几十毫秒，BM25 内存级更快。瓶颈主要在 embedding API 调用（text-embedding-3-small 约 100-200ms）和 rerank 模型推理。评测模式关掉重排序后整体延迟可控制在 500ms 内，在线模式加 rerank 约 1-2 秒。

### 四、知识图谱

#### 16. 为什么要在 RAG 上加知识图谱？解决什么问题？

RAG 是块级匹配，只能检索到相似文本片段。但用户问"文档 A 和文档 B 提到的人物 X 有什么关系"时，单靠语义匹配很难跨文档关联——块里分别提到人物 X 但没有直接建立关系。知识图谱把实体和关系显式化，能从图结构中跨块跨文档推理，回答需要关联多个来源的问题。

#### 17. 知识图谱具体怎么构建的？

核心步骤：1）文档分块后对每块做实体识别（用 LLM 抽取实体及类型），关系抽取（识别实体间的谓词关系）。2）同名实体对齐合并，构建(entity1, relation, entity2)三元组。3）存入图结构（轻量级，用字典/邻接表实现），支持按实体查询关联节点。4）检索时除了向量结果，额外从图中拉取与 query 实体相关的知识作为补充上下文。

#### 18. 图构建是实时的还是异步的？对上传延迟有影响吗？

异步构建。文档上传后先走解析→向量化入库，让用户能立刻开始检索。知识图谱构建在后台异步执行，不阻塞上传流程。文档管理界面展示图构建状态。

#### 19. 实体对齐怎么处理？同名不同实体、不同名同实体？

同名不同实体通过实体类型和上下文判断。比如"张三"出现在两个不相关文档中，通过各自所属的上下文和实体类别区分。不同名同实体（如"马云"和"Jack Ma"）目前简单处理——依赖 LLM 抽取时的判断力，加了提示要求如果有英文名/别称一并标注。精确的对齐需要更复杂的实体链接模块，是后续优化方向。

#### 20. 知识图谱的存储用什么？规模大了怎么办？

当前规模不大，用内存字典+JSON文件持久化即可。通过 embedding 做实体检索召回候选三元组。如果规模上来会考虑 Neo4j 或 NetworkX，支持图遍历查询、子图检索。

### 五、评测与迭代

#### 21. 为什么需要独立检索评测脚本？不是直接看问答效果就行？

端到端问答效果受 LLM 自身能力影响很大——同样检索结果，不同模型回答质量不同。评测脚本把检索环节独立出来，只衡量"该返回的文档有没有返回、排在第几位"，排除 LLM 干扰，才能定位到底是检索不行还是生成不行。修改检索策略后跑评测看指标变化，迭代效率远高于人工测问答。

#### 22. Recall@K 和 MRR@K 分别衡量什么？为什么选这两个指标？

Recall@K 衡量覆盖率——Top-K 结果中命中了多少标注的相关文档，关心"找全了没有"。MRR@K 衡量排序质量——第一个相关文档出现在第几位，关心"对的排在前面没有"。两个指标互补：Recall 好的系统可能把相关文档排很后面，MRR 保证用户体验。实际迭代中先看 Recall 确保不丢，再优化 MRR 提排序。

#### 23. 评测数据从哪来？怎么构造查询集和标注集？

从实际使用场景中采集一批典型查询（30-50 条），覆盖不同难度和类型——精确查询（找具体数据）、模糊查询（问概念）、跨文档查询（需要多文档信息）。标注集人工标注每条 query 对应的相关文档 ID 和相关块 ID。更新文档库时也需要补充新的 query-标注对。标注成本高，但这是检索评测的核心投入。

#### 24. 评测驱动了哪些具体优化？

举几个例子：1）初期纯向量 Recall@5 只有 0.6，加了 BM25 后提到 0.82。2）加了 RRF 融合后 MRR 从 0.45 提到 0.61。3）MMR 压缩前后发现 Recall 几乎不变但 LLM 回答的引用准确率明显提升，因为上下文更聚焦。4）分块大小从 300 调到 500 后 Recall 提升约 5 个百分点。

#### 25. 除了 Recall 和 MRR 你还关注什么指标？检索延迟？Token 利用率？

对，还关注：1）检索延迟 P50/P99——保证用户体验不卡顿。2）上下文利用率——给 LLM 的 context 中有多少比例真正被引用到回答中，这个指标衡量了检索结果的"可用性"而不只是"相关性"。3）去重前后块数比——衡量冗余度。但这些指标没有写入自动化评测，目前是手工抽查看。

### 六、综合追问

#### 26. 如果让你把这个 RAG 系统从 Demo 升级到生产级，会做哪些事情？

1）文档处理队列——目前是同步+异步混合，改为完整的 Celery/RQ 任务队列，支持重试和进度追踪。2）监控和告警——嵌入调用延迟、向量库大小、检索 P99 延迟、上传失败率。3）权限和租户隔离加固。4）检索结果缓存——高频 query 的检索结果加 Redis 缓存。5）A/B 测试框架——不同检索策略线上对比。6）数据漂移监控——用户文档分布变化时重新评估检索效果。

#### 27. 整个项目最大的技术难点是什么？

混合检索的参数调优——RRF 的 k 值、加权比例、MMR 的 λ 值、BM25 的 k1 和 b 参数……参数空间大且互相影响。通过评测脚本批量跑参数组合，找了 3-5 组表现稳定的配置作为不同模式的默认值。另一个难点是表格切分——不能简单按 token 切，需要识别表头、保持行完整性，最终用 Docling 提取的表格结构元数据来指导切分边界。

#### 28. 为什么用 ChromaDB 而不是 Milvus 或 Pinecone？

ChromaDB 部署零成本——pip install 就能用，不需要额外服务。开发阶段和 demo 场景完全够用。如果上生产，Pinecone 的云服务和 Milvus 的分布式能力更强，但当前规模不需要。LangChain 对 ChromaDB 的支持也最完善，换库成本低。
