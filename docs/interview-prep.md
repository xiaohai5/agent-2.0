# 智能旅行助手 App — 面试准备

## 简历描述

> **基于 LangGraph Multi-Agent 的智能旅行助手 App**
> *2025.xx — 至今*
>
> 围绕 Multi-Agent 协作与 MCP 工具调用构建的对话应用，已通过 Capacitor 打包安装到手机使用。
>
> - 基于 LangGraph 编排 MemoryAgent 与 DialogAgent 双 Agent 协作，设计记忆检索—工具准备—生成—记忆更新四阶段流水线
> - 设计基于 Skill 文件的意图路由机制，自动将用户输入分类为旅行规划、车票、餐饮、闲聊、知识检索五个领域，按需动态加载领域上下文
> - 集成高德地图与 12306 的 MCP 服务，封装为 LangChain Tool 交由 Agent 自主决策调用，实现从 POI 搜索到地理编码再到路线规划的链式工具编排
> - 设计 Redis 短期记忆 + Markdown 长期记忆双层记忆架构，超限自动摘要压缩，用户画像自动提取，检索时语义匹配按需加载
> - 构建反馈到 DPO 的数据飞轮：收集用户评分与标注，支持导出 JSONL/JSON/CSV 格式训练集，支撑模型偏好对齐微调
>
> 技术栈：LangGraph, LangChain, MCP, ChromaDB, FastAPI, Redis

## 面试追问与回答

### 1. MemoryAgent 和 DialogAgent 各自的职责边界怎么划分的？

MemoryAgent 只负责记忆的生命周期——从 Redis 检索相关历史、判断是否触发压缩、从对话中提取用户画像写入 Markdown。DialogAgent 负责理解意图、决定是否调工具、生成回复。两者不直接通信，通过 LangGraph 的 State 传递上下文，每个 Agent 只读写自己关心的 State 字段。

### 2. 为什么是四阶段流水线？如果某阶段失败了怎么处理？

拆成四阶段是因为每阶段有明确的输入输出和失败隔离——记忆检索失败不影响后续生成（用空记忆兜底），工具调用超时可以降级为纯文本回复。LangGraph 的节点天然支持异常捕获，异常信息写入 State 后传给下个节点处理。

### 3. State 里都存了什么？怎么控制不膨胀？

存当前对话历史、检索到的记忆片段、工具调用结果、中间思考过程。对话历史设最大轮数限制，记忆片段只存 Top-K 检索结果，工具调用结果用完后立即清理，不随 State 跨轮累积。

### 4. 为什么选 LangGraph 而不是自己写循环或用 CrewAI/AutoGen？

自己写循环控制流复杂、难调试。CrewAI 和 AutoGen 偏 Agent 间对话协作，而这里是流水线式单 Agent 内部阶段拆分，LangGraph 的图执行引擎更匹配。另外 LangGraph 的 checkpoint 机制能回溯每一步 State，出问题时调试效率高很多。

### 5. 路由具体怎么实现的？用模型判断还是规则？

模型判断。将五个模块的定义、路由规则和示例写在 SKILL.md 中，作为 system prompt 的一部分注入。首轮对话时让模型输出模块标签，后续根据标签加载对应 reference 文件。本质上是用 prompt 做零样本分类，而不是训一个独立路由模型。

### 6. 模型分错了怎么办？有没有兜底？

默认兜底到闲聊模块。另外在 SKILL.md 里写了大量示例边界 case，比如"帮我订票"和"查一下车次"都归车票模块。实际使用中准确率很高，因为五个领域边界清晰。

### 7. "按需加载"具体怎么做？加载什么内容？

首轮确定模块后，只将该模块的 reference markdown 文件追加到 system prompt。比如旅行规划模块会加载旅行规划技巧、高德工具使用说明、行程 JSON 格式规范。不相关模块的文件完全不进上下文，控制 token 消耗。

### 8. 如果用户一轮对话里切换了意图怎么办？

每轮都重新过路由判断。上一轮在订车票、这一轮问天气，路由会自动切到闲聊模块。短期记忆里保留上一轮上下文，不会因为模块切换丢失对话连续性。

### 9. MCP 协议在你的项目里具体怎么用的？完整调用链路？

高德和 12306 各启动一个 MCP Server，通过 langchain-mcp-adapters 的 MultiServerMCPClient 连接。启动时自动发现 Server 暴露的所有 tool 并转为 LangChain Tool，每个 Tool 带 name、description、input schema。Agent 用标准的 function calling 机制——模型看到工具描述，判断需要调哪个，生成调用参数，客户端执行后把结果塞回对话上下文。

### 10. 多个工具之间的调用顺序怎么决定的？比如先搜 POI 再算路线？

模型自主决策顺序。比如用户说"从酒店到故宫怎么走"，模型会判断：先调地理编码把"酒店"和"故宫"转成坐标，再调驾车路线规划。这两步是两次独立的 function call，第一次结果回来后模型自动判断需要第二次调用。工具描述里写清楚了前置依赖。

### 11. 工具调用失败或超时怎么处理？

设计了超时熔断——单次 MCP 调用设 30 秒超时，超时后在 State 中标记错误，DialogAgent 看到错误后向用户说明"当前服务繁忙"并尝试给出替代建议。MCP Server 断连时有自动重连逻辑。

### 12. 12306 MCP 实际能用吗？遇到什么坑？

能查到车次、时刻表和余票。坑主要是 12306 接口反爬严格，偶尔会触发验证码导致 MCP 返回异常。处理方式是捕获后降级提示用户"请手动登录 12306 确认"。

### 13. 短期和长期记忆各存什么？为什么不用一个方案解决？

短期记忆存原始对话片段，Redis TTL 7天，用于多轮对话上下文检索。长期记忆存从对话中提取的用户画像——偏好、常去地点、出行习惯，写 Markdown 文件持久化。不合并是因为两者生命周期和检索方式完全不同：短期记忆有时效性、需要过期；长期记忆需要持久、语义检索。

### 14. 压缩摘要怎么做的？会不会丢关键信息？

设置条数上限，超出后取最早的 N 条交给 LLM 做摘要，摘要替换原文。摘要指令里要求"保留时间、地点、人物、关键决策"。压缩率大概 10:1，实测丢失的主要是寒暄内容，关键决策保留完好。

### 15. 用户画像具体怎么提取？触发时机？

每轮对话结束后异步提取——把本轮对话 + 已有画像一起给 LLM，让它判断有没有新信息需要更新画像，有则追加，没有则保持。提取的字段包括：常住城市、出行偏好（高铁/飞机）、饮食偏好、经常去的城市等。

### 16. 语义匹配怎么做的？用什么模型？

把用户当前 query 用 embedding 模型（text-embedding-3-small）向量化，与 Redis 中存储的记忆向量做余弦相似度检索，取 Top-K 条注入上下文。长期记忆也是同样方式——Markdown 文件预先分块向量化存 ChromaDB，检索时按相似度返回最相关的画像片段。

### 17. DPO 数据格式是什么？一条数据长什么样？

DPO 需要 (prompt, chosen, rejected) 三元组。用户的提问文本是 prompt，用户点赞的回复是 chosen，用户踩的回复是 rejected。如果用户只点赞没踩，就用同一 prompt 的另一条未被点赞的回复作为 rejected。导出格式：

```json
{
  "prompt": [{"role": "user", "content": "..."}],
  "chosen": [{"role": "assistant", "content": "..."}],
  "rejected": [{"role": "assistant", "content": "..."}]
}
```

### 18. 数据质量怎么保证？会不会有噪声？

前端收集时要求用户给出评分（赞/踩）和可选文字说明。导出接口支持按时间范围、评分类型过滤。在项目层面主要靠量取胜——积累足够多再人工抽查清洗。

### 19. 这套数据飞轮实际跑起来了吗？

流程已打通：前端提交反馈 → 后端落库 → 导出接口生成 DPO 格式文件 → 可接入 HuggingFace TRL 训练。但模型微调本身需要 GPU 资源和更多数据量，属于项目边界外。

### 20. 为什么用 Capacitor 打包而不是直接做 PWA 或 React Native？

Vue 技术栈，Capacitor 对任何 Web 框架原生支持，不需要重写 UI。相比 PWA，原生安装体验更好，且 Capacitor 的 HTTP 插件能绕过 WebView CORS 问题。相比 React Native，不需要引入额外的跨平台框架。

### 21. 多轮对话中如何保证 Agent 不丢失上下文？

短期记忆每次对话前从 Redis 检索与当前 query 语义相关的历史片段，注入到本轮上下文。即使中间隔了几天，只要记忆还在 TTL 内，就能恢复之前的对话上下文。长期记忆确保用户的基础偏好始终可用。

### 22. 整个系统部署在什么环境？用了什么部署方式？

后端 FastAPI、前端 Nginx、MySQL、Redis 四个服务通过 Docker Compose 编排在一台服务器上。前端 Vue 应用 build 后由 Nginx 托管静态文件并反向代理 `/api` 到 FastAPI 后端，MySQL 和 Redis 数据通过 Docker volume 持久化。
